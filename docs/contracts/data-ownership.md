# Data and ownership contract

Firestore stores Timestamp values; JSON boundaries and fixtures use ISO 8601 UTC strings; Swift uses Date. Store money in integer cents, distances in miles (as supplied), coordinates in decimal degrees. Document `id` is snapshot metadata injected by an adapter, never a persisted field. Optional supplied Swift fields accept absent or null values; maintain this on decoding. Existing field names and collection paths are preserved unless an ADR explicitly changes them.

The schema currently includes all 18 supplied document structs plus embedded Venue, and request/response/draft types. Later-feature document types are reference scaffolding, not implemented features. Known enums are documented in operation specs; many source document status fields remain String until their feature defines the allowed values. Do not infer business semantics from the generated type alone.

**The accounts integration opens only verified self-profile get/update, scoped public company get and shared tags reads. The organizer slice adds same-company reads of `companies/{c}/events/{eventId}`: members read scheduled events only (list queries must constrain companyId, filter `status == 'scheduled'` and specify a limit <=100), organizers (`role == 'admin'`) also read cancelled events. Events are written only by `createEventV1`/`updateEventV1`; `commandReceipts` is server-only. The weekly-theme slice adds same-company verified reads of `companies/{c}/challenges/{id}` (get, including a missing document; member lists need a limit <= 20, organizers may list without one; get also checks `companyId` matches the path); themes are written only by `createChallengeV1`/`updateChallengeV1` and challenge submissions are own-document reads written only by the submission callables (see challenge-submissions.md). Other paths remain denied.** See [exact limits and integration status](accounts-integration.md); the remaining table is target access design, not an assertion that all access is enabled. Each feature PR must implement and test its permitted subset. Admin SDK bypasses Firestore rules, so every function must perform its own authorization.

## Queries and indexes

Feed: `companies/{c}/events` filtered companyId==c, status in [scheduled, completed] (`completed` = closed by an organizer after the event; members keep seeing it in My Events and Memories; cancelled stays organizer-only) and startTime>=the lower bound captured at refresh, ordered by startTime then document ID; paginate using both ordered values, default page 20 and maximum 100. The companyId constraint is required by event list rules; cursors are bound to the UID/company/query. The matching index source includes companyId, status and startTime with the implicit ascending document-ID suffix. Index deployment remains a separate release action; emulator success alone does not prove a production index is ready. My Events: collectionGroup `rsvps`, constrained companyId, userId, status==going, ordered eventStartTime; fetch corresponding events in bounded batches and split Upcoming/Past by current Event.endTime. Rules for collection-group access must explicitly constrain resource companyId and userId; nested path rules alone are insufficient. Attendees: event RSVP subcollection status==going, paginated; do not expose full AppUser profiles for it. A Firestore listener, not the command response, drives joined-state persistence.

Weekly theme (Home): `companies/{c}/challenges` where `endDate >= now` ordered by `endDate`, limit 5, then pick the first with `startDate <= now`; a single-field range served by the automatic index, so no composite index is declared. The server overlap check uses the same single-field `endDate` range. Indexes are tracked in gcp/firestore.indexes.json. Timestamp edits require keeping RSVP.eventStartTime snapshots consistent; index/query release is blocked until the update strategy is tested. Denormalized display names/avatars may be snapshot-at-RSVP in V1; profile propagation is a separate decision.

## Storage

Album objects live at `companies/{c}/events/{eventId}/photos/{uid}/{slot}` (slot 0..19, create-only, <= 10 MiB, jpeg/png/heic), uploaded only by the member into their own folder while their RSVP is `going` and the scheduled event has ended; same-company verified members read them through the authenticated SDK. This replaces the source's planned `{photoId}.jpg` path. No download-token (bearer) URLs are minted; `EventPhoto.downloadURL` is stored empty. Orphans (uploaded, never finalized) are bounded by the 20 slots per member per event; finalizing an invalid object deletes it. Details and the eligibility decision: [event photo albums](callables.md#event-photo-albums). V1 default event images are bundled or approved static assets, not Storage user uploads.

## Internal server data proposals

- `companies.emailDomain` maps a registrable root email domain to its company (ADR 0007). Clients cannot list or query `companies` or write `emailDomain` (rules deny both). Trusted seed/admin tooling must store a lowercase Public Suffix List root domain that is not a personal provider. Uniqueness is not enforceable by Firestore or rules, so it is enforced by process and fail-closed: the seed and `scripts/migrate-company-domains.mjs` refuse duplicates, and the resolver treats a domain claimed by two companies (or a non-root, non-string or differently cased value, which never matches) as NO_COMPANY_FOR_DOMAIN and logs an error. Every subdomain of a mapped root joins that company. The equality query uses the single-field index declared in `gcp/firestore.indexes.json`; no composite index is needed.
- `accountRateLimits/{uid}` holds the fixed-window membership-resolution budget; server-only.
- `companies/{c}/commandReceipts/{uid_requestId}` holds deduplication metadata/payload hash and created event ID; deny clients. Retain for at least the supported client retry lifetime; choose retention before implementation.
- Event.revision (integer >=1) is an intentional addition to the supplied model for concurrent organizer editing. Existing event seeds need revision=1. Never deploy a schema migration implicitly.

## Chat, notification preferences and push data (feature branch, not deployed)

Rules added by `feature/chat-push-backend`, emulator-tested in `gcp/tests/rules/chat-push.test.ts`:

- `companies/{c}/events/{e}/messages/{messageId}`: get/list/create require a verified same-company caller with an RSVP row `status == "going"` for this event. Lists must set `limit <= 100` (recommended query: `orderBy("createdAt", "desc").limit(50)` or `limitToLast`). Create: the document ID is the client-generated `clientMessageId` (`^[A-Za-z0-9_-]{8,128}$`, a UUID is recommended); exactly the fields `companyId`, `eventId`, `authorId`, `authorName`, `authorAvatarId`, `text`, `createdAt`; path-matching IDs, `authorId == auth.uid`, `authorName`/`authorAvatarId` equal to the caller's `users/{uid}` `displayName`/`avatarId`, `text` already trimmed and 1..1000 characters, `createdAt == request.time` (serverTimestamp). The event must exist, be `scheduled` and `request.time < endTime + 24 h` (decision: post-event coordination stays open one day; history remains readable for going participants afterwards, including after cancellation). No update or delete. Because the ID is fixed, a retry can never duplicate a message: if an ambiguous retry is denied, the client reads `messages/{clientMessageId}` and treats an existing own message as sent.
- `companies/{c}/events/{e}/subscriptions/{uid}`: the owner may get it (missing = `none`) and create/update exactly `{level, updatedAt}` with `level` in `all|changes|reminders|none` and `updatedAt == request.time`, only while a same-company RSVP row (going or cancelled) exists. No list, no delete, no other user's document.
- `users/{uid}/devices/**`, `companies/{c}/events/{e}/pushReceipts/**` (exactly-once push claims with an `expireAt` for an optional TTL policy) and `emulatorPushOutbox/**` stay denied to clients. Event documents (including `changeLog`, `updatedBy`) remain client-read-only. No server-owned chat counters or unread data exist yet.

Indexes: collection-group `events` (status, startTime) for the reminder scheduler and a collection-group single-field override on `devices.tokenHash` for token de-duplication across accounts. Rules and indexes require a separate reviewed deployment.
