# V2 — participation and memories

**Deadline: December 4, 2026. Status: planned; this setup branch does not implement these features.**

The committed/stretch distinction follows `V1_V2 Schedule.docx` in the Sprint 3 submission. Acceptance checks are proposed implementation detail derived from that schedule and the testing report. Start from the stable [V1](V1.md) flows and the [contracts](../../contracts/README.md).

Use the [V2 planning handoff](v2/README.md) to assign bounded work after its policy/schema prerequisites are settled. The app lives under `ui/` and Firebase services/tests under `gcp/`. Read root [SESSION.md](../../SESSION.md); each work session gets one log under `docs/sessions/` and may span multiple commits. CI requires at least one new valid session log per PR, not one per commit.

## Committed features

| ID | Feature | Acceptance criteria | Dependencies; lead area, named owner TBD |
| --- | --- | --- | --- |
| V2-01 | Coworker invitations | Invite a coworker within the same company; the recipient can view, accept, or decline. Acceptance joins the event according to the same RSVP/capacity rules as a normal join. | V1 accounts + RSVP; discovery |
| V2-02 | Challenges and submissions | Show challenge requirements and allow progress, caption, and optional photo evidence. Explain the completion requirement, submission method, and reward before submission. | Membership + challenge contract; organizer |
| V2-03 | Attendance and challenge approval | Authorized organizers confirm event attendance and approve challenge submissions. Each qualifying completion awards points once, including under retries or concurrent actions. | RSVP + submission/ledger contracts; organizer + backend |
| V2-04 | Points tracking | Display the user's points balance; approved attendance and challenge completion update it through server-owned transactions. A client cannot award itself points. | V2-03 + ledger; organizer + backend |
| V2-05 | Event photo albums | Upload and view photos associated with past company events; enforce company access for both stored files and metadata. | Storage policy + upload contract; accounts |
| V2-06 | Interest filtering | Filter upcoming events by interest tags. Make the filter state clear and preserve a way to browse all events. | V1 tags + event feed; frontend |
| V2-07 | Integration, fixes, and tests | Verify complete workflows, address prioritized user-testing findings, and achieve greater-than-90% unit test coverage with the measured scope documented. | Every committed feature; all areas |

## Stretch goals — not release commitments

| ID | Feature | Acceptance criteria if selected | Lead area; named owner TBD |
| --- | --- | --- | --- |
| V2-S01 | Activity chat | Event participants send and view text messages within their event. Do not label an attendee list as chat. | Discovery |
| V2-S02 | Raffle eligibility and entry | Show attendance progress toward the raffle requirement; eligible users receive one entry. Automated winner selection remains outside the proposed scope. | Organizer + backend |
| V2-S03 | Rewards redemption | Redeem points for rewards and view redemption codes. Eligibility, inventory, balance changes, and retry behavior follow the server contract. | Organizer + backend |
| V2-S04 | Photo comments and favorites | Comment on and favorite photos; access favorite memories from Profile. | Accounts |
| V2-S05 | In-app notifications | List invitation and challenge-approval updates, open their targets, and mark them read. | Discovery + backend |
| V2-S06 | Venue/weather integration | Display venue information from the selected Places API and weather from Open-Meteo for supported event dates. Handle unavailable data. | Discovery |

The architecture names Foursquare for Places, while the revised schedule says the selected Places API. Confirm that provider before implementing its adapter. Apple/Google sign-in, company clubs, badges, automatic activity tracking, and bulk photo downloads are not committed V2 features in the schedule.

## Handoff checklist

- [ ] Assign owners to committed features before taking on stretch work.
- [ ] Review V2 callable schemas, state transitions, authorization, and error/retry semantics across backend and iOS owners.
- [ ] Test invitation acceptance together with RSVP capacity and membership checks.
- [ ] Test replayed approvals and simultaneous qualifying actions: one ledger effect per qualifying completion.
- [ ] Test photo metadata and Storage access together, including cross-company attempts.
- [ ] Agree on upload limits, permitted formats, retention, and cleanup behavior before uploads ship.
- [ ] Test partial failures and reconciliation for uploads and server-owned counters.
- [ ] Retest challenge instructions; separately retest reward explanations if stretch rewards are selected.
- [ ] Record full workflow checks and greater-than-90% unit coverage; generated code and empty scaffolds are not product coverage.
- [ ] Document any selected stretch goal in its own issue without silently changing the committed milestone.
