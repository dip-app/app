# V1 frontend readiness audit

Audited November 3, 2026 against commit `80e3462` (merged login/navigation and grouped-chat work). This is the **baseline audit**, not a declaration that V1 is complete. Later changes should update the affected rows with their tests and PR evidence.

Scope is the eleven commitments in [V1](../V1.md), not every screen visible in the prototype. **Live** below means a real adapter is wired; **mock** means an in-memory repository supplies the behavior; **missing** means the acceptance behavior has no connected implementation; **manual** identifies verification that code alone cannot establish.

## Next frontend work, in useful order

1. **Event read model and details:** project existing Event start/end, venue/address, cost, capacity and status into UI values; add metadata presentation and explicit missing-value handling. Build deterministic fixtures for free/paid, long address, full, cancelled and past states. Keep SDK/Firestore types out of feature views.
2. **RSVP state and cancellation:** one primary join state, visible leave action, pending/error/retry semantics and observed updates. The mock may exercise the UX but must not be presented as server enforcement. Follow [setRsvpV1](../../contracts/callables.md) and [read/write ownership](../../contracts/data-ownership.md).
3. **My Events and discovery states:** classify with end time, exclude cancelled RSVPs, add stable ordering and empty/error/retry displays. Keep human-readable labels out of classification logic.
4. **Organizer UI packet:** separately owned admin entry and create/edit pages against the existing draft/revision contract. Do not invent permissions, default-image URLs or time-change synchronization behavior.
5. **Sharing and approved imagery:** enrich the native share payload once metadata exists, and integrate the category-image catalog once approved. These do not require new invitation, upload or deep-link features.
6. **Release verification:** meaningful scoped unit coverage, denial/concurrency integration tests, another-laptop build and complete physical-device event flow. Update each readiness row only with concrete evidence.

## Boundary and evidence notes

- The account-aware member host connects real account/profile data while event/RSVP/attendee content remains fixture-backed. “Signed in successfully” does not mean company events are live.
- `gcp/functions/src/index.ts` exports `resolveMembershipV1`; this baseline has no exported V1 event-management or RSVP command. The backend and frontend therefore need parallel coordinated work, not a frontend-only completion label.
- Existing Event and RSVP schemas in `contracts/v1/models.schema.json` already carry the needed metadata. Prefer projections of these contracts over a new wire version for presentation changes.
- The account packet's November 3 completion section records deployment/manual evidence; older introductory prose elsewhere still describes account deployment as pending. This audit follows the newer explicit evidence without claiming to rerun it.
- Challenges, chat/comments, albums/uploads, rewards, points, invitations, notifications and venue/weather services are V2 or stretch work. Their prototype implementation or polish does **not** close a missing V1 row. Weekly-challenge UI and later comment-placement redesign remain separate backlog work.
- This audit inspected source and existing handoffs. It did not execute tests, deploy services, approve imagery, measure coverage or perform a new device check.
