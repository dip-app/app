## Shake to report (review branch `feature/v2-stream-c`, November 11)

Shaking the device (or Profile > "Report a problem") captures the screen and opens a report sheet: category chips, description (1,000 characters), screenshot toggle, optional app details (app version/build, iOS version, device model, locale, route kind and a random install id; never name, email or token), Send with sending/sent/queued/failed states, and an offline queue (5 per uid, 7 days, 2/8/30 s backoff, discarded on sign-out). It is limited to Debug and TestFlight builds, and `dip.shakeToReport.enabled` (default on, Profile toggle) switches the shake off. `BugReportSubmitting` has a mock and a Firestore + Storage adapter. `firestore.rules` gains create-only `bugReports/{reportId}` (verified member, uid == auth.uid, strict allow-list and size limits, no client reads) and `storage.rules` allows an owner-only JPEG at `bugReports/{uid}/{reportId}.jpg` (<= 400 KB, no reads); both have emulator tests. **Nothing is deployed.** The markup editor, shake prompt step and rate limiting are not built (rules cannot rate-limit; see the PR).

## Coworker invitations backend (feature/v2-coworker-invites, November 11)

The `invites` Functions module adds `sendInviteV1`, `respondToInviteV1` and the minimal directory `listCoworkersV1` (name, avatar id and team of same-company members, query of at least 2 characters, rate limited; no company-wide profile list). Invites live at `companies/{c}/invites/{eventId_toUserId}` (sender/recipient reads only, no client writes); acceptance runs the same transaction body as `setRsvpV1` (`applyRsvp`), so a full or closed event leaves the invite pending. The recipient gets an in-app notice (`users/{uid}/notifications`, recipient-readable, isRead-only updates) and a best-effort push through the existing pipeline. Unit, rules and emulator tests are written (`npm run test:invites:integration`, in CI) but were not run when this was written. **Nothing is deployed.** See [callables](docs/contracts/callables.md#coworker-invitations).

## Admin backend (feature/admin-backend, November 11)

The `admin` Functions module implements tickets #121 to #126 ([contract](docs/contracts/admin.md)): roles `member | organizer | admin` with a server-side permission matrix, an append-only `companies/{c}/auditLog` written by every admin command, request-id idempotency receipts and a per-caller rate limit; album moderation (`removeEventPhotoV1`, `removeEventPhotoCommentV1`); attendee management (`addEventAttendeeV1` with capacity override, `removeEventAttendeeV1`, `recordAttendanceV1`); member management (`listMembersV1`, `getMemberV1`, `updateMemberV1`, `resetMemberProfileV1`, `setMemberStatusV1`, `adjustMemberPointsV1`, `upsertTeamV1`); roster pre-provisioning (`upsertRosterEntryV1`, `revokeRosterEntryV1`; `resolveMembershipV1` claims an invited entry or creates a claimed one for everyone who joins, so the roster lists everyone; there is no roster-only mode); and chunked bulk import (`importEmployeesV1` dry run, `applyEmployeeImportV1`, `getEmployeeImportV1`). `updateEventV1` now also accepts the `completed` status. Deactivated members are refused by `resolveMembershipV1`, the callables and the Firestore rules. Unit, rules, contract and emulator tests exist; **nothing is deployed** and the rules/emulator suites have not been run on this branch yet. Challenge callables remain admin-only.
