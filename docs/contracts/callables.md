# Callable endpoint contract

`resolveMembershipV1` is implemented/exported and emulator-tested ([ADR 0007](../adr/0007-oauth-domain-based-sign-in.md)); it is not deployed. The earlier `joinCompanyV1` join-code command was removed before deployment. `createEventV1` and `updateEventV1` are implemented, exported, emulator-tested and deployed to `team05-dip` (November 3, 2026); see [Organizer commands](#organizer-commands-implementation). `setRsvpV1` is implemented (participation module, emulator-tested) and exported; deployed to `team05-dip` (November 8, 2026). Deploy filters must include the codebase: `firebase deploy --only functions:dip:setRsvpV1` (`functions:setRsvpV1` matches nothing). Other operations below remain **unimplemented**. V1 request/response types are executable schemas; V2 describes the next handoff and requires expansion before its implementation. Firebase v2 `onCall`, proposed region `us-central1`, Node 22. Swift uses `Functions.functions(region: "us-central1").httpsCallable("setRsvpV1")`; endpoints are named exports, not guessed REST URLs. Region needs the team's GCP/data-location decision before deployment.

Firebase Auth handles sign-in; V1 supports Google sign-in only (ADR 0007), with no email/password, verification-email or join-code flow. Every callable requires a valid Firebase user. Use the SDK's callable error mapping; no custom success/error envelope. Payloads and responses carry `contractVersion: 1`. Derive the caller UID from Auth. Look up the server-owned `users/{uid}` membership for every company operation; never trust client role, companyId, balance, counters, or a supplied userId as authorization. resolveMembershipV1 enforces App Check outside the official Functions emulator. A deployed client must configure its provider/debug workflow before rollout; production is not bypassed.

## V1 operations

| Export | Request -> response schema | Permission | Atomic behavior and retry contract |
|---|---|---|---|
| `resolveMembershipV1` | ResolveMembershipRequest (`{ contractVersion: 1 }` only) -> ResolveMembershipResponse | Signed in with sign-in provider `google.com` and `email_verified` | Everything comes from the ID token; the payload carries no domain, company, role or name. Reduce the email domain to its registrable root with the Public Suffix List (`eng.acme.com` -> `acme.com`), reject personal providers (gmail.com etc.) with PERSONAL_EMAIL_DOMAIN before any read, then find the single company whose `emailDomain` equals the root (Admin query inside the transaction; zero or more than one match); unmatched or ambiguous -> NO_COMPANY_FOR_DOMAIN. In one transaction create users/{auth.uid} with role member, balance 0, email from the token, displayName from the token `name` (fallback email local part, max 80) and documented empty defaults (strings empty, lists empty, radius 20, createdAt server time). Existing same-company member returns its membership and only refreshes a changed OAuth displayName; a different-company account fails with MEMBERSHIP_CONFLICT. Never promotes a user. Five eligible attempts per verified UID per fixed server-clock minute, including successes and unmapped domains; invalid, unauthenticated, non-Google, unverified and personal-domain requests do not consume the budget. The profile listener, not the acknowledgement, establishes membership in the client. |
| `setRsvpV1` | SetRsvpRequest -> SetRsvpResponse | Same-company member acting for self | Transaction reads event + own RSVP. `going` requires scheduled, future start and available capacity unless already going. `cancelled` may cancel before start; after start fails. Update RSVP and attendeeCount in the same transaction, retaining cancelled row. Repeating the same state is a no-op; no underflow. Rejoining sets going once. Concurrent last-seat attempts admit at most one user. |
| `createEventV1` | CreateEventRequest -> CreateEventResponse | Same-company admin (V1 organizer) | requestId is a UUID retained by the caller across retries. Store a private company+uid+requestId deduplication record and event in one transaction. Same request returns same event ID and revision; same key with different payload fails. Server assigns companyId, createdBy, createdAt, attendeeCount=0, pointsValue=0, status=scheduled, revision=1. |
| `updateEventV1` | UpdateEventRequest -> UpdateEventResponse | Same-company admin | Full draft replacement and scheduled/cancelled status; no hard deletion in V1. expectedRevision guards lost updates. Transaction increments revision; mismatch returns aborted and client reloads before retry. Capacity cannot be below active attendeeCount. Editing times propagates denormalized RSVP eventStartTime with an explicitly tested strategy before release. |

EventDraft is a full writable payload; startTime/endTime are RFC3339 UTC, end > start, start in future when creating. Capacity is 1..10000, costCents is a nonnegative integer, title 1..120 chars, description 1..5000. Schema validates syntax; application layer validates time ordering, tag existence, venue coordinate bounds (-90..90/-180..180), string trimming, same-company references, and URL policy. Server defaults V1 coverImageURL from the chosen category; incoming URL must match the approved default-image catalog. V1 does not upload user images. The catalog is pending design asset approval.

RSVP server snapshots userName/userAvatarId/userDepartment/userJobTitle (optional, additive) and eventStartTime from trusted records. companyId/eventId/userId match the path; checkedIn=false, checkedInAt=null on first creation, createdAt server timestamp. Cancellation does not award points or erase attendance. Response is an acknowledgement; Firestore listeners remain the source of rendered event/RSVP state. Disable duplicate UI submissions while in flight, but rely on server transactions for correctness.

## Errors

| Callable error code | Meaning | Frontend action |
|---|---|---|
| unauthenticated | No valid Firebase Auth user | Sign in again |
| invalid-argument | Shape, version, IDs, fields or date validation failed | Show field errors; do not retry unchanged |
| permission-denied | Membership/admin check failed, non-Google provider, unverified email, or personal email domain (PERSONAL_EMAIL_DOMAIN) | Explain access failure; never silently select another tenant |
| not-found | Authorized tenant resource absent, or no company for the email domain (NO_COMPANY_FOR_DOMAIN) | Refresh, or explain the company isn't on DIP; don't reveal other company data |
| failed-precondition | Closed/past event, conflicting membership, or reused requestId with changed payload | Show reason and reload relevant state |
| resource-exhausted | Event full or membership-resolution rate limit | Show capacity/try-later message |
| aborted | Event revision conflict | Reload and ask user to reconcile edits |
| unavailable / deadline-exceeded | Transient service/network issue | Retry safely under operation's rule; preserve requestId |
| internal | Unexpected failure | Generic user message; log correlation ID without personal data, emails or tokens |

Use HttpsError details `{ reason: <stable machine code>, fields?: [<field names>] }`; no secrets or internal stack traces. Proposed reason values include EVENT_FULL, EVENT_CLOSED, REVISION_CONFLICT, MEMBERSHIP_CONFLICT, VALIDATION_FAILED, RATE_LIMITED, EMAIL_NOT_VERIFIED, PROVIDER_NOT_ALLOWED, PERSONAL_EMAIL_DOMAIN, NO_COMPANY_FOR_DOMAIN and INVALID_STORED_MEMBERSHIP. Error details are advisory; unknown reasons fall back to the code. A timed-out update is ambiguous: reload event revision/content before issuing a new update. RSVP acknowledgements may show a newer global attendeeCount on a later retry.

## V2 committed command map

These operations are design contracts to finalize with schemas and feature tests before work begins, not callable stubs or exports.

| Proposed export | Payload -> response | Invariants |
|---|---|---|
| `recordAttendanceV1` | RecordAttendanceRequest -> RecordAttendanceResponse | Admin confirms same-company going RSVP. Transaction sets checkedIn + server time and appends deterministic ledger entry `attendance_{eventId}_{uid}` once. Reject no RSVP/cancelled or invalid event window. Repeated approval awards 0 new points. Policy for attendance window/reversal remains open. |
| `approveChallengeV1` | ApproveChallengeRequest -> ApproveChallengeResponse | Admin approves existing same-company pending submission. Deterministic ledger key `challenge_{challengeId}_{uid}` prevents repeat awards. Update balance, submission and counters atomically. Repeated approval awards 0 new points; no negative/reversal flow until specified. |
| `submitChallengeV1` | companyId, challengeId, progress, caption, optional photo path -> submissionId, status | Caller owns submission `{challengeId}_{uid}`. Validate goal units/window/evidence, require same-company Storage path; client never approves or awards points. Server owns status and counters. |
| `sendInviteV1` | companyId, eventId, toUserId, message, requestId -> inviteId, status | Same-company sender/recipient; no cross-company lookup or notification leak. Request replay returns same invite. |
| `respondToInviteV1` | companyId, inviteId, response accepted/declined -> inviteId, status, RSVP status | Recipient only; accept uses the same capacity transaction as RSVP; no partial accepted invite if event is full. Replay is safe. |
| `finalizeEventPhotoV1` | companyId, eventId, photoId, storagePath, caption -> photoId | Authenticated same-company participant; finalized upload metadata and file ownership validated server-side. Event must be past; retries by photoId don't duplicate metadata. Upload object ownership/MIME/size and orphan cleanup policy must be settled before uploads open. |

All carry contractVersion=1. Notifications are server-authored documents. Counts and points are server-owned. Private deduplication records, membership code lookup and ledger uniqueness are implementation collections outside public DTOs.

## V2 stretch boundaries

Chat/comments: direct client writes may be enabled with membership, event participation, author ownership, allowed-field, length and server timestamp rules. Favorites: own profile allowed-field update. Rewards redemption: a future `redeemRewardV1(companyId,rewardId,requestId)` transaction checks eligibility, stock and balance, appends a unique ledger deduction and returns a private code; payload/schema/code-use policy needs a separate ADR. Raffle entries are server-created once per user/raffle; no automated draw. Venue/weather integrations go through backend adapters with secrets and quota controls; never expose partner API secrets in Swift. In-app invite/approval notifications are recipient-only reads with isRead-only client edits. These are not V1 endpoints.

The [V1 account integration](accounts-integration.md) records limiter semantics, editable-profile rules, Swift session ownership and emulator commands. Generated schemas are unchanged.

## Organizer commands (implementation)

`createEventV1` and `updateEventV1` live in `gcp/functions/src/modules/organizer` (domain validation, application services, Firestore transaction adapter, thin `onCall` transport) with the same App Check policy as `resolveMembershipV1`. Deployed to `team05-dip` (us-central1) on November 3, 2026 together with the event read rules; no organizer has been assigned yet, so every caller is still refused `NOT_ORGANIZER`.

- **Authorization:** caller must be a verified Google user whose server-owned `users/{uid}` has `role == "admin"`; the supplied `companyId` must equal that membership's company, otherwise `permission-denied` with reason `NOT_ORGANIZER` or `COMPANY_MISMATCH`. Roles are assigned manually by trusted admin tooling; clients cannot write them.
- **Reasons (`details.reason`):** `UNAUTHENTICATED`, `VALIDATION_FAILED` (with `details.fields`), `NOT_ORGANIZER`, `COMPANY_MISMATCH`, `EVENT_NOT_FOUND`, `REVISION_CONFLICT` (`aborted`), `CAPACITY_BELOW_ATTENDEES`, `TIME_CHANGE_BLOCKED`, `REQUEST_REUSED`, `TAG_NOT_FOUND`.
- **Create:** payload is validated strictly (unknown keys rejected, UTC `Z` timestamps, end after start, start in the future, capacity 1..10000, integer cents, coordinate bounds, tags exist in `tags/`, at most 10 unique tags, cover URL in the approved catalog). The deduplication receipt `companies/{c}/commandReceipts/{uid}_{requestId}` stores a SHA-256 of the normalized draft; the event and receipt are created in one transaction, so concurrent replays create one event and a reused key with different content fails `REQUEST_REUSED`. Server assigns `companyId`, `createdBy`, `createdAt`, `attendeeCount: 0`, `pointsValue: 0`, `status: "scheduled"`, `revision: 1`.
- **Update:** full-draft replacement plus `status` (`scheduled`/`cancelled`, never deleted), guarded by `expectedRevision`; capacity cannot fall below `attendeeCount`.
- **Time lock (V1 decision, issue #14):** if **any** RSVP record exists for the event, including cancelled ones, both `startTime` and `endTime` are locked (`TIME_CHANGE_BLOCKED`, fields `startTime` and `endTime`). RSVP `eventStartTime` snapshots cannot be rewritten in one transaction (up to 10,000 RSVPs), and cancelled records keep a snapshot too. Every other validated field and the cancelled status remain editable. Relax it only with an agreed, tested synchronization strategy.
- **Placeholders and decisions:** `APPROVED_COVER_URLS` (the design-approved catalog is pending). Create-request receipts are compact and retained without automatic deletion (issue #14).

## Notifications, chat and change history

Branch `feature/chat-push-backend` (module `gcp/functions/src/modules/notifications`). Implemented, unit-, rules- and emulator-tested; exported from `gcp/functions/src/index.ts`; **not deployed**. Sending real pushes additionally requires an APNs authentication key from the paid Apple Developer team uploaded to the Firebase project, plus iOS push entitlements; both are separate authorized steps. Schemas: `RegisterDeviceRequest/Response`, `UnregisterDeviceRequest/Response`, `DeviceRegistration`, `EventSubscription`, `EventMessage`, `EventChangeLogEntry`, `EventFieldChange`, `PushNotificationData` and the optional `Event.changeLog`/`Event.updatedBy` (all additive).

| Export | Kind | Contract |
|---|---|---|
| `registerDeviceV1` | callable | RegisterDeviceRequest `{contractVersion: 1, token, platform: "ios", appVersion}` -> `{contractVersion: 1, deviceId}`. Verified Google user with a server-owned membership (`MEMBERSHIP_REQUIRED` otherwise). Upserts `users/{uid}/devices/{sha256hex(token)}` with a server `updatedAt`; idempotent. In the same transaction removes that token from any other user (shared phone switched accounts) and evicts the least recently refreshed devices beyond 10 per user. Unknown fields (e.g. a supplied userId) fail `VALIDATION_FAILED`. |
| `unregisterDeviceV1` | callable | `{contractVersion: 1, token}` -> `{contractVersion: 1, removed}`. Any signed-in caller; deletes only their own registration; idempotent. Call before sign-out. |
| `onEventMessageCreated` | Firestore create trigger, `messages/{id}` | Push to subscribers with level `all` who still have a `going` RSVP, excluding the author. Once per message (`pushReceipts/chat_{messageId}`). |
| `onEventChanged` | Firestore update trigger, `events/{id}` | Appends `changeLog` and pushes the one-line change summary to `all`/`changes` subscribers except the editor (see below). |
| `onUserProfileUpdated` | Firestore update trigger, `users/{userId}` | When `displayName`, `avatarId`, `department` or `jobTitle` change, updates only the snapshot fields (`userName`, `userAvatarId`, `userDepartment`, `userJobTitle`) on the user's `rsvps/{uid}` for company events that have not ended or ended within 30 days (events queried by `endTime`, at most 500, no collection-group query). Skips unchanged values; never touches `status`, counts or attendance. Existing RSVPs are filled once by `gcp/scripts/backfill-rsvp-profile.mjs` (dry-run by default). |
| `onRsvpChanged` | Firestore write trigger, `rsvps/{uid}` | Reconciles the default subscription from current state: going without a subscription -> create `{level: "changes"}`; not going -> delete the subscription unless the member changed it after that RSVP write. `setRsvpV1`'s contract and transaction are unchanged. |
| `sendEventReminders` | Cloud Scheduler `every 15 minutes` (Etc/UTC) | Reminders to `all`/`changes`/`reminders` subscribers when start is (20 h, 24 h] away ("24h") and (0, 60 min] away ("1h"). Exactly once per event, window and startTime via a create-only `pushReceipts/reminder_{window}_{startMillis}` claim, so retries and overlapping runs never double-send. Only `status == "scheduled"` future events are selected (collection-group `events` index on status+startTime). |

**Levels** (owner to confirm): `all` = chat + changes + reminders; `changes` = changes + reminders (default on join); `reminders` = reminders only; `none` (or a missing document) = nothing. Users without registered tokens are skipped.

**Push payload.** `notification: {title: event title (<=60), body}`; chat body is `"{authorName}: {first 80 chars}"`, other kinds contain no user-written text. `data` (strings, `PushNotificationData`): `type` (`chat` | `event_changed` | `reminder`), `companyId`, `eventId`, `deepLink` (`dip://events/{eventId}` or `dip://events/{eventId}/chat`), plus `messageId` (chat), `revision` (event_changed) or `window` (`24h` | `1h`). APNs `thread-id` is `event-{eventId}`; change and reminder pushes set `apns-collapse-id`. The iOS app should route on `type` + `eventId` and re-read Firestore (tenant rules apply); the `dip` URL scheme is not registered yet. FCM is called with registration tokens (`sendEachForMulticast`, 500 per batch); tokens reported `registration-token-not-registered`/`invalid-registration-token` are deleted. Pushes are best-effort and at most once per claim; a crash between claim and send drops that push rather than duplicating it.

**Change history.** On each event update the trigger diffs user-visible fields only (`title`, `description`, `tagIds` (order-insensitive), `coverImageURL`, `startTime`, `endTime`, `venue.name/address/locality`, `costCents`, `costNote`, `capacity`, `isOutdoor`, `status`) and appends `{at: update time, by, revision, changes: [{field, from, to}]}` to `changeLog` (values are display strings: RFC3339 UTC times, `"a, b"` tags, decimal numbers, `"true"/"false"`, text truncated to 200 chars; `null` when absent). `by` is `updatedBy`, which `updateEventV1` now records server-side on each revision, or `"organizer"` for writers that do not bump the revision. Writes touching only `changeLog`, `attendeeCount`, `revision`, `updatedBy` or other non-tracked fields add nothing, which ends the trigger's self-write loop. An entry with the same revision and identical changes is a duplicate delivery and is skipped (no second push). Capped at the latest 50 entries, oldest first. Edits to cancelled-and-still-cancelled or ended events are logged but not pushed. updateEventV1's request/response are unchanged.

**Emulator.** With `FUNCTIONS_EMULATOR=true` pushes are written to the server-only `emulatorPushOutbox` collection instead of FCM (`npm run test:notifications:integration`). The scheduler is not run by the emulator; reminder logic is covered by unit tests with a fake clock.

## Weekly themes (implementation)

A weekly theme **is** a `Challenge` (`companies/{companyId}/challenges/{challengeId}`, `type: "weekly"`). `createChallengeV1` and `updateChallengeV1` live in `gcp/functions/src/modules/challenges` (same layering, App Check policy, auth and error envelope as the organizer commands) and are exported from `gcp/functions/src/index.ts`. They are **not deployed**; deployment and production seeding are a separate authorized step.

- **Schemas (additive, contracts/v1):** `ChallengeDraft`, `CreateChallengeRequest/Response`, `UpdateChallengeRequest/Response`; `Challenge` gained optional `createdBy`, `createdAt`, `updatedAt`, `revision`. No existing field changed.
- **Create:** `{ contractVersion: 1, companyId, requestId (UUID), draft: ChallengeDraft }` -> `{ contractVersion: 1, challengeId, revision, challenge: Challenge, replayed }`. A replay with the same requestId and draft returns the current stored challenge with `replayed: true`; the same key with another draft fails `REQUEST_REUSED`. Receipts are `companies/{c}/commandReceipts/challenge_{uid}_{requestId}` (`kind: "challenge"`, SHA-256 of the normalized draft, challengeId), created in the same transaction as the challenge. The window may have started (publish this week's theme mid-week) but `endDate` must be in the future. Server assigns `companyId`, `createdBy`, `createdAt`/`updatedAt` (server clock, whole seconds), `participantCount: 0`, `completedCount: 0`, `revision: 1`.
- **Update:** `{ contractVersion: 1, companyId, challengeId, expectedRevision, draft }` -> `{ contractVersion: 1, challengeId, revision, challenge }`. Full-draft replacement; mismatch -> `aborted` `REVISION_CONFLICT` (reload, then retry). Counts, author and `createdAt` are never written. No deletion in V1.
- **Window lock (V1 decision):** once `participantCount > 0` or `completedCount > 0`, `startDate` cannot change and `endDate` may move (longer or shorter) only to a time that is not in the past; otherwise `failed-precondition` `WINDOW_CHANGE_BLOCKED` with the blocked fields. Unchanged dates always pass, so text/goal/reward edits stay possible.
- **Validation (`invalid-argument` `VALIDATION_FAILED`, `details.fields`):** unknown/missing keys (reported as `draft.<key>`), title 1..60 and description 1..1000 (trimmed), `type == "weekly"`, `goal` number in (0, 10000], `goalUnit` 1..24, `pointsReward` integer 0..1000, at most 10 unique tag IDs (unknown tags -> `TAG_NOT_FOUND`), RFC3339 UTC `Z` dates, `endDate > startDate`, span <= 14 days, `coverImageURL` in `APPROVED_THEME_URLS` (currently only `catalog://theme/fitness`; the URL selects a bundled illustration, never a photo).
- **One current theme:** windows (inclusive) of two `weekly` challenges in one company may not overlap -> `failed-precondition` `CHALLENGE_WINDOW_OVERLAP`, fields `startDate`/`endDate`, plus `details.conflict = { challengeId, startDate, endDate }` of the earliest conflicting same-company theme. The check is a transactional single-field range query on `endDate` (no composite index).
- **Reasons:** `UNAUTHENTICATED`, `VALIDATION_FAILED`, `NOT_ORGANIZER`, `COMPANY_MISMATCH` (`permission-denied`), `CHALLENGE_NOT_FOUND` (`not-found`), `REVISION_CONFLICT` (`aborted`), `REQUEST_REUSED`, `TAG_NOT_FOUND` (`invalid-argument`), `CHALLENGE_WINDOW_OVERLAP`, `WINDOW_CHANGE_BLOCKED` (`failed-precondition`), `INVALID_STORED_CHALLENGE` (`internal`, generic message).
- **Seed:** `scripts/seed-weekly-theme.mjs` (dry-run by default) creates the Fitness theme with deterministic IDs `weekly-fitness-<yyyymmdd>`; see the script header.
